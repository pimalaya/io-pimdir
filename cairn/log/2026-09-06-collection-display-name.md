# A collection can be named, not only addressed

The crate has been writing `collections.name` since the first migration and has never once written a name into it. `ensure_collection` and `set_collection_kind` both insert `:collection` twice, once as the id and once as the name, and no statement updated it afterwards, so the column has always been a copy of the key.

That only shows once an owner namespaces its ids, which neverest does by source: its stores read `imap/Archives`, `carddav/Default` and `caldav/ED99C7C8-2741-11F1-9B88-2C202A48A29D`. For mail the label is merely ugly. For DAV it is useless, the id being a path segment servers routinely make a UUID, and pimalaya-linux had already built a private `app_collection_name` table and a display-name resolver rather than render one.

## What landed

- **The statement** (capability `store`). `set_collection_name` re-vendored from the sibling checkout, so `sql::SET_COLLECTION_NAME` is generated by build.rs and tests/spec_drift.rs proves the copy byte for byte. It inserts with an undeclared kind when the row is absent, the way `ensure_collection` does, and updates only `name` when it is present, so a kind and an account already recorded survive it.
- **`PimdirSourceStore::set_collection_name`**, beside `ensure_collection` and `set_collection_account`, binding the handle's own account exactly as they do.
- **tests/collection_name.rs.** A collection declared through `ensure_collection` is seeded with its id; the setter moves the label and leaves the id, the kind and the account where they were; moving it stamps the collection in the change feed, and restating the same name stamps nothing, which is the `collections_stamp_update` trigger's "observable column moved" rule doing its job.

`color`, `description` and `sort_order` keep the same gap deliberately: nothing reads them yet.
