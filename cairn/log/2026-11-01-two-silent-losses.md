# Two silent losses

pimdir 3d6a04e (branch audit-2026-10-31, untagged) folds two rules into storage-draft-08 and sync-draft-07, no draft number moving (pimdir cairn/changes/two-silent-losses-fold-into-draft-08): a conflict settles only by an overrule or by a person's resolution naming it, and a writer finding its final name held verifies the file there. spec/ re-vendored from it byte for byte (`git -C ../pimdir archive 3d6a04ed812c6e3312ac8d2fee6b96d0dd6bc677 migrations queries vectors payloads`, the four directories removed first), spec/REVISION moved. The sync vectors move to format 3 (every case, an `Edit`'s `resolves`, an object stated after the run), 124 to 130 are new, payloads.json gains seven `resolves` cases (41).

## A resolution names its conflict

- `PimdirMutation::Edit` gains `resolves: Option<Vec<PimdirHash>>` (**breaking** for a struct literal). An `Edit` without `overrule` meets its item's conflict when the item is conflicted and its binding's when the placement carries a `conflict_revision`; meeting either it is refused, staging nothing, as `PimdirMutateError::Unresolved { handle, met, resolves }` unless `resolves` names the `conflict_object` of each, and so is one stating `resolves` and meeting none; an unread body is named by none (src/mutate.rs `conflicts_met`, `resolved`). `PimdirMutateError::code()` is new, `conflict-unresolved` among its seven codes. The `Settle` op is now staged only by a resolution meeting an item conflict, where it was staged for any non-overruling edit of a placement projecting `Conflict` or `Tombstone`.
- The mutation cannot see the item, so the load states it: `PimdirLoaded::conflicted` (**breaking** for a struct literal), the loaded placements whose item is conflicted with the item's diverging body, filled by `PimdirStore`'s load and the drain from the new `PimdirHub::conflicted`. A storage leaving it empty for a placement it projects `Conflict` with no binding conflict reads as an unread item conflict, refused, never settled silently.
- `PimdirAction::Update` gains `resolves`, encoded as the payload's `resolves` and read strictly as a non-empty array of distinct names (src/codec.rs `hashes`; **breaking** for a struct literal). The drain hands it to the `Edit`, so an update meeting a conflict it does not resolve parks with the refusal's message, which names the diverging body. A resolution runs through a conflicted binding whose body it names when the item has one, in source order (STORAGE §15.2, src/client/producer.rs `stage_action`); an unbound item's update checks its item's conflict on the same terms (`unresolved`). The CLI's queue listing prints `resolves`.
- The overlay (src/client/reader.rs `PimdirStanding`) reads, for each item a pending update edits, the item's conflict and its conflicted bindings, and folds an ordinary update only over no conflict at all and a resolution only when it names the item's body, where conflicted, and a conflicted binding's or, the item conflicted, finds none: the binding the drain runs through is the owner's choice, so the overlay may hide an update the drain applies but never shows one it parks. A folded resolution settles what it names for the rows after it.
- Tests stating a person's settle now state `resolves`: the six cells of tests/item_conflict_settle.rs, tests/engine's resolution helpers and property steps (through `Client::shown`, the bodies a resolution form shows), the mutate unit tests of a binding conflict, whose op list loses the `Settle` a binding conflict never needed. `duo_edit` in tests/engine/property.rs now asserts an ordinary edit over a conflict is refused; the random edits elsewhere already tolerated a refusal.

## A name held is verified

- `PimdirBlobs::write` and `settle` verify a file found under the final name, on the skip and on the no-replace move's `AlreadyExists` alike: one hashing to it is kept, one failing it fails the write as `InvalidData` carrying the name (`blobs::held_name`), the temporary left for the caller.
- An owner moves it into quarantine/ and writes again: `PimdirSourceStore::write` drops its share of the writer lock, calls `PimdirStore::quarantine` (staging lock exclusive, writer lock exclusive, verified again) and stages again, once per name; `PimdirStore::put_item` does the same inside its transaction; an owner's `PimdirBlobStage` (`stage_body`, a writer's `commit`) takes the locks without waiting (`PimdirLock::try_collecting`, `owns`) and fails the write where it cannot. A producer moves nothing: its `stage_body`, `blob_writer` commit and enqueue with a body fail as `PimdirError::Io` naming the name, nothing enqueued.
- `write::apply` no longer writes a `StoreObject`'s bytes: every caller stages them before the transaction, and writing them again would read each body back whole to verify the name it just wrote.
