# Payloads and capabilities

Phase 4 of the-crate-follows-storage-draft-08. The queue's payloads follow pimdir's schemas under payloads/ (pimdir d671bbd, the structure-security-and-wording entry's "The queue's payloads are typed" and "Annex B names every capability once", the sync-rules-and-the-write-contract entry's "The producer's gate is advice; the owner's backstop decides"): the codec reads each action and intent at `v: 1` exactly as its schema types it, a producer refuses a malformed payload and the drain parks one, the owner's backstop covers intents, `x-vtodo` is `calendar.component.vtodo`, and a producer has the two rewrites STORAGE §18 and Annex B.1 ask of it. tests/payloads.rs passes all 34 payloads, the 13 phase-4 lines off tests/pending_vectors.txt.

## What landed

- **The codec** (src/codec.rs). `action_from_payload` reads every kind through `members`, which parses the JSON object, reads `v` first (another version is still `UnknownVersion`, skipped, never parked) and refuses a member the kind does not define as the new `PimdirActionError::UnknownField(member)`; then each member through one reader per placeholder of STORAGE §15.3: `seq` (an integer from 1), `label` (a non-empty string: `key`, `id`, `collection`, `addr`, `label`), `text` (any string), `hash` (an object name, `PimdirHash::is_name`), `flags` (an array of distinct flags `is_flag` accepts) and `required`. An `add` requires `flags` and `object`, a `set-flags` `flags`; `supersedes` is an object of exactly `collection` and `seq`, its members named `supersedes.collection` and `supersedes.seq`; a `set-performer`'s capability follows Annex B's grammar (`capability::is_name`, the schema's pattern). `MissingField` now means a member missing alone; a member of another type or breaking its rule is `Invalid { field, reason }`, where it was `MissingField` for both. An Annex B.2 intent is read by its type in src/intent.rs and kept as `PimdirAction::Unknown`; an application's own kind is read as a JSON object at `v: 1` alone, its members its own.
- **Why the valid `submit` was refused**: the vector names no `object`, and `PimdirSubmit::from_payload` required one, the message's hash. The schema defines no such member (Annex B.2: "the message as the action's body", STORAGE §15.3: "The body is the column's"), so the message is the row's `queue.object_hash` alone: `PimdirSubmit` lost its `object` field, `to_action(message)` takes it and sets the action's `object_hash`, and a payload naming `object` is refused as an undefined member. `PimdirQueueRow::action` fills an intent's `object_hash` from the row, and `action_from_payload`, reading a payload alone, names no body for an opaque action (it read the payload's `object` by "shared convention", parking an application's intent whose `object` was no string).
- **The intents** (src/intent.rs). `PimdirSubmit`, `PimdirCollectionCreate` and `PimdirInvitation` require `source` (`String`, was `Option<String>`), as the four schemas do; `from` is non-empty (the null path went with the schema's `minLength`); `rcpts` an array of non-empty strings, at least one; a `partstat` outside the three is `Invalid` (it was `MissingField`); an item named by both or neither of `seq` and `link_id` is `Invalid { field: "seq" }`; a cancel stating `partstat` is an undefined member. Each type's `validate` holds the value rules `to_action` and `from_payload` share. `PimdirProducer::enqueue_collection_create` resolves the performer before building the intent, so a blank name is now refused after `NoPerformer` rather than before it.
- **The enqueue** (src/client/producer.rs `append`, src/client.rs `replace_action`): the action is encoded, then read back through `action_from_payload` before anything is gated or written, a refusal answered as `PimdirError::Action` (`action-malformed`) naming the member; a later version this crate does not know is queued as it stands. An `add` without its `object` and a flag set never read (encoded `null`) are refused there, where they were queued. `PimdirError::Flag` still answers a flag the store cannot hold first, as before.
- **The drain**: a row whose payload does not read parks with the error, which names the member, an intent's included (they were skipped whatever they held). `pimdir item restore` of an item whose flags were never read now queues the empty set, the only crate path that queued an unknown one.
- **The owner's backstop** (D8, src/client/capability.rs `backstop_intent`). The gate the drain runs before applying an action already read the producer's rows, `calendar.component.vtodo` included (`gate_vtodo` through `gate`), and parked naming the capability and the source (`PimdirRefusal`'s message, tests/capabilities.rs `the_owner_parks_a_task_into_a_calendar_refusing_tasks`). Intents never reached it: the drain skipped every opaque action first. It now parks an Annex B.2 intent whose `source` declares something but not the intent's capability at the anchor (`list_capability_sources`), or not the copy or occurrence it asks for (`intent_option`, shared with the gate), naming both; a source declaring nothing is skipped, since an owner declares every source it runs (STORAGE §15.6) and leaves pending an intent naming one it does not run (§15.2). The producer's gate stays, documented as advice the crate follows.
- **The capability names** (src/capability.rs). `X_VTODO` (`x-vtodo`) is `CALENDAR_COMPONENT_VTODO` (`calendar.component.vtodo`), kept out of `CALENDAR` since a declaration writes it only where the owner knows it; src/client/capability.rs, src/client/reader.rs and tests/capabilities.rs follow. Every other name the module defines was already Annex B's, the 29 of the base set (`mail.submit.copy`, `calendar.reply.occurrence` and `calendar.cancel.occurrence` among them); `every_capability_follows_annex_bs_grammar_in_its_domain` checks the 30 against the grammar and their domain. `collection.create`'s doc now reads its domain as `collection`, where it said it had none.
- **`X-PIMDIR-` stripped** (STORAGE §18). `summary::strip_instructions` removes every logical line whose property name, any case and any group, begins with `X-PIMDIR-`, its folds with it, keeping every other line byte for byte (`summary::logical_lines`, the bytes of each logical line beside its unfolded text). `PimdirProducer::enqueue_foreign_body` runs it on a body bound for a calendar or an address book before `enqueue_with_body_checked`, the action built from the stripped body's hash; a mail body is queued whole, its header no property. Paths judged: the crate builds no resource it did not receive. `pimdir item restore` queues the store's own retained body, which the user or a source wrote there as it stands; a tag queues flags; a performer's replacing `add` (`replace_action`) files the sent message, mail; the gate's probe `add` of a `move` is never queued. A resource from elsewhere enters through a consumer (an invitation added from a message in himalaya or calendula, an import), which is why the method is the API, the caller knowing where the bytes came from.
- **`SCHEDULE-AGENT=NONE`** (Annex B.1). No API recorded the user's acceptance: tests wrote the parameter by hand. `summary::calendar::unschedule` writes it on every `ORGANIZER` and `ATTENDEE` lacking `CLIENT` or `NONE` of every component naming an `ATTENDEE`, components read as `scheduled` reads them (children of the root, time zones aside, an alarm's attendee not the component's), replacing another agent the line states, a rewritten line folded at 75 octets on a character boundary with the line's own ending; `scheduled` and `unschedule` share `notified`, and contact.rs's colon split is `split_value`, shared with `PimdirContentLine::parse`. It is the narrowest API the spec implies: a function the producer runs on the refused body, the result enqueued as any other.

## Departures

- `recurrence_id` is refused unless it is `YYYYMMDD` or `YYYYMMDDTHHMMSS[Z]`, as before, where its schema takes any string: B.2's prose fixes its form, and a performer parks one naming no occurrence anyway.
- A `rcpts` entry or a `name` holding only spaces is refused, as before, where the schema's `minLength` takes it; a `name` holding a control character too (B.2: no separator of the provider).
- A JSON number with a fraction of zero (`5.0`) is no `seq` here, where JSON Schema 2020-12 reads it as an integer; no vector holds one.

## Notes for pimdir

- payloads/submit.v1.schema.json's `from` has `minLength: 1`, so a `submit` cannot state the null reverse-path (RFC 5321 §4.5.5) the crate's type used to allow; the prose's `addr` agrees. Worth a line if a performer ever needs it (a bounce), else nothing.
- B.2's `recurrence_id` is typed `text?` and its schema a bare string, while the prose fixes its form; a pattern would let a producer and a performer refuse the same values.
- STORAGE §15.6's backstop says an intent whose `source` "does not declare its capability" MUST be parked, and §15.2 that an owner not running the source an intent names leaves it pending. A source with no row is both; this crate reads the second for it, since an owner declares every source it runs. One sentence in §15.6 would settle which.
