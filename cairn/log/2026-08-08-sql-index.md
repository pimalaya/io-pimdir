# The canonical SQL, reachable by name

`sql` has always been dependency-free on purpose: `client` is the only gated
module, so a consumer holding its own SQLite driver can take the schema and the
statements and run them itself. Nothing made that practical across a language
boundary, though: sixty separate `pub const`s are reachable from Rust and from
nothing else, so such a consumer had to write an accessor per statement or
transcribe all sixty and let them drift from the spec in silence.

`sql::ALL` pairs each constant's name with its text, `MIGRATION_0001` included
(creating the database is as much a consumer's job as querying it) and `VERSION`
excluded (an integer, not SQL). One serialization hands the whole canonical SQL
across a boundary, and lookups are by name.

The immediate consumer is the Pimalaya Android app. Android ships SQLite and the
app's storage seam already drives `android.database.sqlite` from Java through a
JNI upcall, so taking `client` would have compiled a second SQLite engine into
every ABI of a binary whose first design goal is to be small. It takes `sql`
instead and executes the statements on the platform driver.

The index is hand-written, so two tests derive their expectations from the
module's own source with `include_str!`: one asserts every declared constant is
indexed, the other that the index follows the declaration order, which keeps it a
line-for-line mirror of the module and makes a wrong pairing visible on review.

A third test was written and removed. It asserted no two statements share text,
to catch a name paired with the wrong constant, and it failed immediately on
`DELETE_ACTION` and `CANCEL_ACTION`. Those are deliberately one delete under two
names, documented as such where they are declared: the trigger is a request in
one case and an apply in the other. The test was wrong, not the code, so it went
rather than the duplication.

No statement changed, and the `client` driver is untouched.
