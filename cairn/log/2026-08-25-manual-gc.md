# A store never collects itself

`collect_garbage` ran inside `write`, `write_rekeyed`, `apply_queued`, `drop_action`, `purge` and `purge_retained_before`: every write deleted the object rows at refcount zero and unlinked their blobs after the commit. It is gone from all six, and `PimdirStore::collect_garbage` is a verb somebody calls. Capabilities `store` and `cli` moved, and the format moved with them (pimdir `no-write-collects`).

## What landed

- **No write collects** (capability `store`). Refcounts are maintained exactly as before; only the reclamation left. An object at refcount zero is unreferenced, not deleted. This is the data-loss fix: spec §14 invites a consumer to stream a body to its sharded path and index it without holding it whole, and `STORE_OBJECT` inserts at refcount zero because references come from placement pointers only — so a consumer that stored bodies in one batch and attached them in the next lost them at the end of the first, silently, bytes included. tests/gc.rs opens with exactly that batch pair.

- **`PimdirStore::collect_garbage`**, the collector: the object rows at refcount zero, and every blob file the index does not name. Those are one case rather than two — once the rows are gone, their bodies are orphans — so it is one pass over the tree rather than an unlink per row plus a sweep. It reports rows, files and bytes.

- **No grace window.** The collector takes the staging lock exclusively and runs on an owning handle that already holds the owner lock (`single-owner-lock`), so neither an owner nor a producer can be mid-write while it sweeps. The hour-long grace period the format required a few hours earlier was standing in for exactly those locks; a period-prefixed temporary file is still left alone, since it belongs to a writer that has not renamed it into place.

- **`pimdir gc`** (capability `cli`), reporting what it freed and refusing rather than waiting when a producer holds the staging lock.

- **`check` became diagnosis, `--fix` became repair.** `--fix` used to unlink orphan blobs behind `--grace` and a confirmation, which was the backwards half of the old arrangement: the routine operation (every write) swept with no guard at all, and the exceptional verb was the careful one. Both flags are gone. `--fix` now recomputes the drifted refcounts with the canonical `recompute_refcounts` — which §7 permits, and which nothing did — and clears the bindings whose item is gone. `check` also lost its own blob-tree walk to `PimdirBlobs::files`, which the collector needed anyway.

- **A purge reports rows retired.** `PimdirPurgeReport` loses `bytes`; the bytes belong to whatever frees them.

## Deviations

- **`clear_dangling_bindings` clears only bindings.** The task said "clears dangling rows", and `check` reports three kinds. Two of them are not garbage: an item whose object row is missing is still the item, and a queue row whose body is missing is still an intent somebody expressed. Deleting either destroys data rather than repairing it, so they stay reported. A binding with no item is genuinely unreachable, and that is the one the repair takes.

- **No `json_schema.rs` entry.** The task called for one, and this repository has no such file: its `*Output` types derive `Serialize` and implement `Display`, and none of them derives `JsonSchema`. `GcOutput` follows the repository rather than the convention.

- **The collector refuses a staging producer rather than waiting.** `PimdirError::Staging` is a new variant. A producer holds its shared lock for its handle's lifetime, so a collector that waited would be waiting on a program's lifetime rather than on an operation; a hang is the one failure mode an operator cannot act on.
