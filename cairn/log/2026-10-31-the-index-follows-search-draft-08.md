# The index follows search-draft-08

Phase 6 of the-crate-follows-storage-draft-08, after pimdir's 2026-10-31-search-terms-bounds-and-versions (pimdir d671bbd), the "index knows its store" rule of 2026-10-31-format-identity-and-versions, the thread prune the erasure rule of 2026-10-31-structure-security-and-wording cites, and C6 of 2026-10-31-checks-run-every-statement-and-pin-every-vector (queries.json at `v` 2, `cut`). The 8 phase-6 queries cases pass and left tests/pending_vectors.txt, which is now empty.

## What landed

- **The query limits** (SEARCH §8.3, §8.4; src/search/query.rs). `LENGTH_MAX` (1,024 scalar values), `GROUPS_MAX` (32 groups open at once) and `TERMS_MAX` (128 terms), refused as `PimdirQueryErrorCode::LimitExceeded` (`limit-exceeded`): the length before the lexer, spanning from the 1,025th value to the end; the nesting in the parentheses pass (`balance`) beside an unbalanced parenthesis, the leftmost fault answering, spanning the `(` opening the 33rd group; the count in the descent when the 129th term is read, before its field, value and wildcard checks. `NESTING_MAX` and the descent's depth parameter are gone: the descent recurses per group alone, the nesting bound checked before it runs, and a run of `not` is a loop.
- **The occurrence bounds and the cut** (SEARCH §7, §8.2; src/search/occurrence.rs). `OCCURRENCES_MAX` 10,000, the first by start then end of those overlapping the horizon; `PERIODS_MAX` 1,000,000: for each `RRULE` the start of its first unexamined period is computed on the series' clock from `DTSTART`'s period (the instant for `SECONDLY` to `HOURLY`, the day, the `WKST` week, the month, the year) plus 1,000,000 times `INTERVAL` units, and when it lies before the horizon's end and neither the rule's `UNTIL` nor its `COUNT` (walked through `IcalRecurExpand`, bounded by both) ends it first, the rule is stopped there and no occurrence starting from it is written. The item's cut is the earlier of that instant and its 10,001st occurrence's start (`Expansion = (Vec<(i64, i64)>, Option<i64>)`), written with its occurrences (`PimdirIndexOp::ReplaceOccurrences::cut`, `set_cut`). `PimdirSearchCoverage::cut` counts `cut_before` over the query's collections for a query with a date term and a calendar collection in scope, its end the top-level range's, `NULL` when open; `is_complete` is false while it is not 0; the CLI prints it (`cut` in JSON, a line in text).
- **The index's version, shape and store** (SEARCH §2, §4; src/client/search.rs `held`, `PimdirIndexHeld`). `open` reads what index.db holds before writing anything, the WAL pragma moved out of `connect` until the index is found its own or built: a schema without `index_meta`, a `shape` other than `canonical`, a `format_version` above `search-draft-08` or naming no draft (`search-v1` included) is `PimdirError::IndexVersion { path, version, shape }` (`index-version`), never rebuilt, written nor deleted; an earlier draft or no `format_version` column is rebuilt; at this version, another schema version, tokenizer or schema text, another `store_id` or `store_incarnation`, or a `store_change` above the store's last stamp is rebuilt. `refresh` makes the same check under index.lock and rebuilds (`build`) an index a store was restored under. `open_query` answers `IndexVersion` for any other shape or version and `IndexOutdated` for the rest. `sql::search::FORMAT_VERSION`, `FORMAT_DRAFT` and `SHAPE`.
- **The floating zone** (SEARCH §7). `PimdirIndexRefresh::floating_zone` and `PimdirIndexRefreshOptions::floating_zone` (`UTC` default, `search::occurrence::FLOATING_ZONE`); an occurrence ical-rs reads floating (a floating time, a date, a `TZID` no zone defines) is moved into the zone through `summary::calendar::iana` (now `pub(crate)`), the offset before a transition, the walk widened by a day each side and the overlap tested on the moved instants; the period limit of a floating series is moved alike. A zone other than `index_meta.floating_zone` re-expands every live calendar item (`WantsReexpand::floating_zone`, bound to `items_to_reexpand`) and is recorded with the horizon (`SetFloatingZone`, `set_floating_zone`). An unknown zone is `PimdirError::IndexZone` (`index-zone-unknown`), checked against jiff's bundled database before the lock. The CLI's `index` and every refreshing command take `--floating-zone ZONE`.
- **The missing retry** (SEARCH §4). A live row whose indexable body was neither indexed nor read is followed by `PutMissing` (`insert_missing`), any other live row by `DropMissing` (`delete_missing`); a dropped placement takes its row by cascade. A run whose `PimdirIndexRefresh::missing` is set (true by default; `PimdirIndex::refresh` sets it on a pass's first run alone) yields `WantsMissing` before the feed, answered by `load_missing_items` and folded as feed rows, whether or not the store stamped them. `WantsUnread` and `LOAD_UNREAD_BODIES` are gone.
- **The thread prune** (SEARCH §9, §4). `placements_gone` is read by its three columns (`PimdirIndexGonePlacement`, with the link id). When the relink reads a touched message holding a `message` row and no mail placement, the run first writes `PruneThread(thread)` for each such thread (`unparent_messages`, then `prune_messages`), reads the rows left (`WantsThreadRows`, `thread_rows`, `PimdirIndexThreadRow`), reads every touched message and those rows again, and re-keys them as seeds of the relink; `DropThread` runs `delete_thread`. The relink (src/search/thread.rs) no longer reparents a message no placement holds: the canonical statements alone unparent and delete, and a component holding no present member is pruned through `PruneThread` too. `PimdirIndexOp::DropMessage`, `DELETE_MESSAGE` and `DELETE_THREAD_UNUSED` are gone.
- **The coverage and the probes** (SEARCH §8.2). An answer's bodiless counts come from the canonical `coverage` on the index connection with the `collections` slot (the store's own `COUNT_BODILESS` stays for `PimdirReader::search_coverage`; the temporal axis moved to `PimdirReader::search_temporal`). What a hit matched is probed for a page's hits alone: each positive text term (`compile::Probe`) against a body its placements hold (`match_object`), else the summary of one indexed bodiless (`match_summary`); the statement's per-hit `matched` subquery is gone, and `rank` is read for the `relevance` order alone.
- **A query of many terms** (src/client/search/compile.rs). The 128-term vector case failed against the bundled SQLite 3.54.1 with "VIEWs and/or subqueries nested too deep" and passed against the system SQLite: 3.54's guard of 2026-10-04 (`checkSubqueryNestingDepth` after `nTab` reaches `SQLITE_LIMIT_EXPR_DEPTH`) counts the cursors every CTE expansion allocates, and each text term's `t<n>` CTE, holding `match_objects` and `match_summaries` with their joins, was expanded once in `hits`, twice through `matched` and again through the final select. Each text term (and `person:`) is now read once, through the same canonical statements, into the connection's `temp.term_match` (`CREATE_TERM_MATCH`, created by `connect`; `CLEAR_TERM_MATCH`) before the query runs (`Compiled::matches`, run by `PimdirIndex::compile`), and the query tests membership in that table by the term's number; `matched` reads the positive terms' rows in one scan. The 50,000-message scale test is unchanged in time (below).
- **Own statements now canonical** (src/sql/search.rs): `DELETE_THREAD_UNUSED` is `delete_thread`; `LOAD_ITEM_IN_REPLY_TO` and `LOAD_ITEM_CATEGORIES` give way to the store's `load_in_reply_to_by_link` and `load_categories_by_link`, bound to one link id in the `links` slot; `LOAD_UNREAD_BODIES` to `load_missing_items`; `DELETE_MESSAGE` to `prune_messages`. The own statements left (`COUNT_UNINDEXED`, `LOAD_HIT_PLACEMENTS`, `LOAD_ENDS`, `LOAD_PLACEMENT`, `TASK_CATEGORY_VALUES`, `MESSAGE_PRESENCE`, `MESSAGE_HASH`, `MESSAGE_IN_REPLY_TO`, `LOAD_MESSAGE`, `MESSAGE_CHILDREN`, `HIT_THREAD`, `THREAD_SPAN`, and the two `term_match` ones) have no canonical equivalent.
- **The runner** (tests/search.rs) compares a case's `cut` with the answer's coverage; queries.json at `v` 2, 168 cases and the occurrence windows, items 26 to 28 included, all pass.

## Departures

- `match_objects_ranked` is run by no answer. The client orders `relevance` over the whole hit set in one statement, bodies and bodiless placements' summaries ranked together; a page of the best bodies alone would leave summary matches out of the order, and §8.2 makes the ranked page a MAY. The probes are run where a page is described, not to walk the store's order: the hit set is still read whole, its text terms through `match_objects` and `match_summaries` ("one matching few is read first").
- The period bound is computed from the rule, not counted while walking: ical-rs's expander skips periods a `BYxxx` part rules out, so it cannot report the periods it examined. The 10,001 first occurrences of each timeline are taken in identity order before the item's are ordered by start, so an override moving an instance from past them to before them is not written (SEARCH §7's invariant, every occurrence starting before the cut written, holds otherwise).
- A floating occurrence is read in the zone by moving ical-rs's UTC reading of its wall time; its end is moved by the same rule, so an occurrence spanning a transition keeps its wall-clock length.
- The missing record is cleared by a `DropMissing` on every live folded row that is not missing, one statement per row, rather than by reading whether it was recorded.
- A pass's first run alone folds the missing placements (`PimdirIndexRefresh::missing`); a consumer of another shape running every run with it set folds them once per batch.

## Notes for pimdir

- SEARCH §7 says an item a bound "stops" records its cut; checks/vectors.py records the period cut only when the millionth period starts before the horizon's end (`if period == PERIODS` before `if at >= high`), so a daily series, examined to 2,739 years on, is not cut. This crate reads it so; the prose could say "before the horizon's end".
- SQLite 3.54 (its fix of 2026-10-04 in `sqlite3WithExpand`) refuses a statement whose CTE expansions allocate 1,000 cursors or more as "VIEWs and/or subqueries nested too deep". A query client inlining `match_objects` and `match_summaries` per text term, as §8.5's "bound as `:match` to `match_objects` and `match_summaries`" invites, meets it well below 128 terms once a term is referenced from more than one place; checks/vectors.py and checks/floor.sh run SQLite 3.50.4 and 3.18.2, where the 128-term case passes. SEARCH could say a query of many terms reads each term's matches apart.
- `thread_rows` answers each row's lowest sort key, '' included for an undated one; a re-keying computing `first` and `last` (the latest dated key) needs `MESSAGE_PRESENCE`'s own reads beside it, which this crate keeps.
