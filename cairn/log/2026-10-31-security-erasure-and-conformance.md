# Security, erasure and conformance

Phase 7, the last, of the-crate-follows-storage-draft-08, after pimdir's 2026-10-31-structure-security-and-wording ("Security considerations", "Erasure", "Conformance is stated once"; STORAGE §8, §9.2, §11.5, §17, §18, SYNC §12, SEARCH §12). A store's files are its user's alone, a lock file is opened without following a link, every database is opened untrusted, a recorded error is scrubbed, an item can be erased from both files, the user empties quarantine/, and README states the crate's conformance. The change is landed.

## What landed

- **Modes** (STORAGE §18; src/client/modes.rs, public): `create_dir_all` and `create_dir` make directories `0700` (`DirBuilderExt::mode`), `options` an `OpenOptions` creating files `0600`, `exposed` reads a path's permission bits and owner, `create_database` creates pimdir.db or index.db empty and `0600` before SQLite opens it, `check` refuses a store. The store directory and every parent `PimdirStore::open` makes, objects/, the shards, quarantine/ are `0700`; a blob, a writer's temporary and a quarantined body `0600`; the three lock files `0600` by their own open. SQLite gives `-wal`, `-shm` and a journal the database file's own mode (`findCreateFileMode` and the shared-memory open copy `st_mode`), so creating the database first is enough: verified with the bundled SQLite and the system one (`--no-default-features --features cli`). The directory a store is created in (no pimdir.db there) is restricted `0700` by `modes::restrict`, whoever made it. `pimdir export` creates its dump the same way.
- **A store others can read** (STORAGE §18, a SHOULD): every profile (`open`, `open_current`, `PimdirReader::open`, `PimdirProducer::open`, the index through its reader) refuses, before opening anything, a store whose directory or pimdir.db has a group or other permission bit set, or another owner than the process's effective user (`rustix::process::geteuid`, rustix's `process` feature added), as the new `PimdirError::Exposed(path)` (`store-exposed`) naming it. Chosen: refused, not opened on the user's word; the user's word is the `chmod`, which the error's sentence names. An option to open anyway would be one more constructor per profile, and a store the user shares on purpose is a backup, not a store.
- **Link-free lock opens** (decision 9; src/client/lock.rs `open`, shared by owner.lock, objects.lock and index.lock): on Unix `rustix::fs::open` with `O_CREAT | O_RDWR | O_NOFOLLOW | O_CLOEXEC`, mode `0600`, a refused open told from a disk failure by `symlink_metadata` and reported `Exposed` naming the lock file; on Windows `std::os::windows::fs::OpenOptionsExt::custom_flags(FILE_FLAG_OPEN_REPARSE_POINT)` (`0x0020_0000`, which std does not name) then the opened file read back by `metadata().file_type().is_symlink()`, a link failing the same way; elsewhere an `lstat` before the open. The Windows item compiles by reasoning alone: the nix shell holds the host target only.
- **Untrusted opens** (STORAGE §18, a SHOULD): `prepare_connection` sets `PRAGMA trusted_schema = OFF` and `SQLITE_DBCONFIG_DEFENSIVE` (`Connection::set_db_config`, on SQLite 3.26 or later, an older one having no such flag) on every connection, read-only ones and the index's included. "From elsewhere" is read as always: the canonical schemas and statements run under both (pimdir's invariant "untrusted: …"), the crate registers no SQL function, and every suite passes under them, so telling a store the crate created from one it did not would buy nothing.
- **Erasure** (decision 8, STORAGE §11.5): `PimdirStore::erase(collection, seq)` answers `PimdirEraseReport { erased, collected }`: `purge` when the item is retained, else `delete_unbound` by its link id when it is live and no source binds it (a bound live item is not purged, `erased` false); `collect_garbage`; then `client::checkpoint`, `PRAGMA main.wal_checkpoint(TRUNCATE)` until it reports `busy` 0 and every frame checkpointed, at most `CHECKPOINT_TRIES` (3) waits on the busy timeout before `PimdirError::Busy`. The collector and the checkpoint run whether or not an item was purged, so an erase a reader stopped finishes when run again. `PimdirIndex::erase()` (feature `search`) refreshes the whole feed in the floating zone `index_meta` records (the refresh options' default `UTC` would re-expand every calendar item into another zone), takes index.lock, runs `optimize_text` and checkpoints index.db the same way. `pimdir item erase SEQ [--collection] [--yes]` locates the item, refuses a live one a source syncs, asks, erases the store, then the index when index.db exists (`ItemEraseOutput`, `pimdir-item-erase`).
- **The thread prune's gap** (SEARCH §9; src/search/refresh.rs): the erase test found the erased mail's key in index.db, in its `thread` row. The phase-6 relink pruned the thread of a message that left (`unparent_messages`, `prune_messages`) and re-keyed the rows `thread_rows` answered, but a thread whose every row the prune removed answered none, so no seed reached it and `delete_thread` never ran for it: a message alone in its thread left its thread row. The relink now records the pruned threads (`Relink::threads`) and emits `PimdirIndexOp::DropThread` for each after its own ops, `delete_thread` keeping a row a message still points to. tests/search.rs `a_lone_message_that_leaves_drops_its_thread_row` compares with a rebuild and failed before.
- **Quarantine emptied by the user** (STORAGE §7): `PimdirStore::empty_quarantine()` answers `PimdirQuarantineReport { files, bytes, left }`, unlinking every file and link of quarantine/ (read by `symlink_metadata`, a link unlinked as itself) and leaving anything else, under the staging lock taken exclusively (`PimdirError::Staging` while a producer stages) and the process's writer lock, as a move into it holds them. CLI `pimdir quarantine empty [--yes]` (`QuarantineEmptyOutput`, `pimdir-quarantine-empty`), a group of its own (hidden alias `quarantines`) rather than a `gc` flag: `gc` never asks and never touches quarantine/, while this destroys what may be a body's only copy and asks first.
- **Error text scrubbed** (STORAGE §9.2, §18; src/security.rs `scrub`, no_std): a URL's userinfo (`scheme://***@host`), the value of `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` to the end of its line, a `Bearer` token, and the value after `=` or `:` of a key ending in `password`, `passwd`, `pwd`, `token`, `secret`, `apikey`, `api_key` or `api-key`, quoted or not, each written `***`. The audit: `park_action`'s `:error` is the one statement recording error text (`queue.error`), reached through `PimdirStore::fail_action`, which the drain and any consumer's performer call, so `fail_action` scrubs; the drain's own reasons are the crate's text. `checkpoint`, the round cursors, `capabilities.detail` and `retained_by` are a connector's or the crate's own values, which no error reaches (a connector's duty under SYNC §12). Errors the crate returns are not recorded and keep their text; the CLI contacts no server.
- **Names as paths** (STORAGE §18; src/security.rs `path_component`): the audit found no path the crate builds from a name: `pimdir export` numbers its item files and lays bodies by their checked hash, `item export` writes where the user says, and no verb saves an attachment or mirrors a folder. `path_component` is offered to the consumers that do (a file source mirroring a folder, an attachment saved): `/`, `\`, NUL, every control character and the bidirectional formatting characters §18 lists become `_`, an empty name, `.` and `..` underscores, so the answer is one component.
- **The level-0 cleanup** phase 1 noted: `codec::level_from_int`'s doc and test no longer read a `0` an earlier draft wrote (the schema's `CHECK` holds 1 or 2), and `PimdirLevel`'s doc lost the sentence.
- **README**: the conformance statement exactly as pimdir asks, `storage-draft-08 owner, sync-draft-07 engine, search-draft-08 indexer (canonical) and query client`, read against STORAGE §17 (the owner profile holds the reader's and the producer's, each a handle here), SYNC §12 (engine; the connector is a consumer's) and SEARCH §12 (indexer and query client, canonical shape); the reinstall note as an `[!IMPORTANT]` block; the deviations (Annex A.1 without `charset-tables`, §18's access list on Windows); GUIDE §1 replaced by STORAGE §17 for what each profile owes; the features and usage lines for erase, quarantine and the modes. Every draft name it holds is the pinned one.
- **The pending helper**: tests/pending_vectors.txt stays empty; on a scratch copy an injected failure in one objects.json case was caught per case and failed the suite at the settle.
- **CHANGELOG** read as a net diff against 0.8.0: the lines naming an intermediate draft (storage-draft-05, -06, -07, search-draft-05, -07, sync-draft-05, draft-04) rewritten as the state they left; the churn of a feature added inside the window removed (every `search` change, removal and fix after the feature's own Added lines, the "Breaking since a8bfbf0" lines, `PimdirNotCurrent::Shape`, the `store-newer` code, `set_derivation` raising then setting, `charset-tables` reading unknown labels as UTF-8 then literal, quarantine "emptied by hand"); the phase-7 lines added, with a Security section.

## Departures

- Windows: no access list granting the user alone is set (std names no access-list call), a store's directories and files take the one their parent hands down, and nothing is refused there as exposed; README lists it as a deviation from §18's MUST.
- pimdir.db is checkpointed by `PimdirStore::erase`, before the index's refresh, rather than after it: the index reads the store through a read-only attachment, which writes no frame, so the order of §11.5 holds for the bytes.
- The erase is two calls, `PimdirStore::erase` then `PimdirIndex::erase`, the CLI running both: the store never depends on its index (`PimdirIndex::refresh`'s own contract), and one call would need a `search`-gated statement inside a store method.
- A store whose group bit is set is refused even where the group is the user's private one: the check cannot tell a private group from a shared one.
